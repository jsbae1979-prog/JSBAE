## 2. 이전 방법과 복구 보존

원본169 DB와 백업A/B의 기존 승인 SHA-256 일치를 확인한 뒤, **검증된 백업B를 안정된 읽기 전용 이전 원본으로 사용**했다. 현재 실행 중인 운영 DB를 raw copy하거나 원본 DB에 migration을 실행하지 않았다.

1. 동일 Windows SID의 원본 파일 소유 관계와 새 전용 경로를 확인했다.
2. 백업B의 DB는 `mode=ro&immutable=1`, `query_only` 연결에서 SQLite `backup()`으로 새 비공개 스냅샷을 만들었다. WAL/SHM을 DB와 따로 복사하지 않았다. 원본·백업에 SQLite가 sidecar를 만들지 않도록 했다.
3. 암호문·설정·미디어는 opaque bytes로 복사했다. 복사 전후 해시를 비교하고 기존 `offline.restore` 절차로 새 프로필에만 복원했다.
4. 새 사용자 데이터의 형제 폴더 `before-first-start/`에 원래 복원 상태와 snapshot index를 보존했다. 실패 시 신규 프로세스만 정상 종료한 뒤 이 스냅샷으로 **신규 프로필만** 복구할 수 있다. 이번에는 실제 실패 복구가 필요하지 않았다.
5. 기존0건 DB는 사용·병합·덮어쓰기하지 않았다. 기존169 원본·WAL·SHM·미디어·인증자료·백업A/B에는 쓰지 않았다.

## 7. 운영 전환 판정·업데이트·정리 후보

**신규 설치·데이터 이전·읽기 전용 React 확인은 인수 가능하다.** 원본을 건드리지 않고 새로운 프로필에서 기존 자료를 확인할 기술 조건은 충족했다.

**실사용 운영 전환은 CONDITIONAL**: 현재 검증 전용 읽기 모드와 자동 실행/복호화 차단은 유지한다. 사용자용 시작 동선, 로컬 편집/저장 허용 범위, 실제 키 사용 및 자동화 재활성화 범위를 먼저 확정해야 한다. 이는 기존 운영본 교체 승인을 의미하지 않으며, 이번에는 운영 교체·삭제·외부 배포를 수행하지 않았다. 실제 유료 API·OAuth·SNS·Windows DPI는 이번 작업에서 NOT VERIFIED다.

Update BAT는 그대로 비활성이다. 실제 배포자 인증서·신뢰 앵커·서명이 없으며 무서명 업데이트를 허용하지 않는다. 실제 업데이트/새 ZIP 작성은0회다. 미확인 샘플12개와 FFmpeg 외부 재배포 조건도 기존 상태를 유지한다.
