# NewsFlow AI — Phase 5D 사전 분석: 기존 기능과 신규 기능

작성: 2026-10-15(KST). 대상: 기준 브랜치 `feat/newsflow-phase5c1` @ `830117894464f29ea572f6bdd2d67a02063fc96a`, 작업 브랜치 `feat/newsflow-phase5d`. 방법: 영상 엔진·영상 서비스·GUI·DB·자동 제작·외부 AI 게이트·테스트/CI·보안 기본 요소·5D 설계 초안의 10개 영역을 코드 기준으로 읽고, 별도 검토자가 누락과 오류를 확인했습니다. 지시의 원칙 "스토리보드, 장면 자동 분할, 타이밍, 자막, 소재 적용 기능을 중복 구현하지 않는다"에 따라 아래 표의 기존 기능은 **그대로 재사용**하고, 없는 기능만 새로 만들었습니다.

## 3. 설계 결정

1. **자동 제작(Autopilot)에는 넣지 않았습니다.** 유료 생성은 장면별로 사람이 소재와 프롬프트를 고르고, 예상 비용 확인과 최종 합성 승인이라는 두 번의 명시적 승인을 거쳐야 합니다. 자동 제작의 6단계 흐름에 넣으면 승인 경계가 흐려지므로 AI 고품질 모드는 영상 스튜디오(`/video` → `/video/ai`)의 독립 흐름으로 두었습니다. 자동 제작 영상은 지금처럼 카드만 씁니다(5C.1 설계 초안 §2의 자동 제작 연동안은 채택하지 않음).
2. **장면 소재 기본값은 카드**이고 AI 생성은 장면마다 고릅니다. 5C.1 설계 초안의 "코드 고정 모델 허용 목록·자동 장면 선정"은 공급사 사실을 확인하지 못한 상태에서 코드에 넣을 수 없으므로, 사용자가 공식 문서에서 확인한 모델·단가·허용 길이를 입력하고 확인 체크를 하는 방식으로 바꿨습니다.
3. **비용은 보수적으로 셉니다.** 보내지 않은 요청만 빼고 실패·정책 거부·취소·결과 불명 요청도 이번 달 사용액에 넣습니다(환불 규칙 NOT VERIFIED).
4. **받아들여졌을 수 있는 제출은 자동으로 다시 보내지 않습니다.** 공급사가 429·408(요청 과다·요청 시간 초과)로 받지 않은 요청만 같은 시도 안에서 같은 Idempotency-Key로 최대 3번 다시 보내고, 보낸 뒤 결과를 모르는 요청은 '결과 불명'으로 두고 사용자가 공급사 대시보드를 확인한 뒤 실패로 확정해야 다시 보낼 수 있습니다.

## 4. 분석에서 발견해 고친 결함

분석·테스트 작성 과정에서 발견한 결함은 모두 고쳤고, 각 결함에 회귀 테스트가 있습니다.

| 결함 | 수정 |
| --- | --- |
| 0010 되돌리기가 테이블을 다시 만들어 외래키로 영상 장면이 지워지거나 실패 | 0008/0009처럼 열만 제자리에서 삭제 |
| 합성이 끝나도 계획 상태가 '최종 합성 중'에 머묾(화면이 계속 새로고침) | 목록·계획·상태 API를 읽을 때 렌더 작업 결과로 상태 갱신 |
| 합성 실패 후 같은 계획을 다시 합성할 수 없어 비용을 낸 클립이 묶임 | 실패·중단된 합성은 장면 수정과 재합성 허용(추가 생성 비용 없음) |
| 완료 후 다운로드·검증 실패 시 새 유료 요청 외에 방법이 없음 | 같은 요청의 결과를 최대 3번 다시 받기(제한시간으로 닫힌 장면 포함), 제한시간이 지나도 공급사가 완료라고 답하면 내려받음 |
| 정책을 통과하지 못하는 저장 프롬프트 하나가 작업자 전체를 멈춤 | 보내기 직전 재검사, 실패 시 그 장면만 '보내지 않음'으로 취소 |
| 작업자 예외(유니코드 숫자 Content-Length 등)로 장면이 '내려받는 중'에 영구 정지 | 장면 단위로 모든 예외를 분류, ASCII 숫자만 허용 |
| 키가 들어간 프롬프트가 SQLite에 저장됨 | 장면 저장 단계에서 키(와 키 ID·비밀값 각각)를 검사해 거부 |
| 잘못된 키·모델 경로가 '보낸 뒤 결과 불명'으로 비용 계산 | 보내기 전 검사 실패는 '보내지 않음'으로 분류, 헤더 주입 차단 |
| API·다운로드 요청이 `Host: 주소:443`을 보냄 | 포트 없는 Host 헤더 |
| 서명된 결과 주소의 쿼리가 RSS 자격 증명 규칙에 걸려 결과를 못 받을 위험 | 다운로드는 쿼리를 분리해 길이·문자만 검사(주소는 저장·기록하지 않음) |
| 프롬프트 정책이 '실제영상'·'deep fake'·제어 문자·주소를 통과 | 띄어쓰기·하이픈 무시 비교, Cc/Cf 문자와 URL·이메일 거부 |
| 클립 장면과 카드 장면의 H.264 헤더 차이(SAR·색 정보)로 `-c copy` 이어 붙이기가 첫 장면 헤더만 유지 | 클립 필터에서 화면비·색 표시를 비워 장면 파일 헤더를 바이트 단위로 일치 |
| 검토한 클립과 합성한 클립이 같은지 확인하지 않음 | 승인 시와 렌더 직전에 SHA-256 비교, 프로젝트 스냅숏·작업 메타데이터에 기록 |
| 클립 문제가 '완성 MP4 실패'로 안내됨 | 렌더 오류 종류 `clip`과 "AI 생성 장면 파일" 안내 |
| 게시 준비에서 AI 장면 영상을 'AI 표시 불필요'로 통과시킬 수 있음 | AI 장면이 있으면 `disclose`만 통과 |
| AI 장면이 계획 화면 밖(영상 작업·보관함)에서 구분되지 않음 | 작업 화면 장면별 소재 표시와 "AI 생성 장면 포함" 표시 |
| 디스크 여유 공간 확인 없이 다운로드 | 200 MiB + 512 MiB 여유가 없으면 받지 않고 다시 받기 가능 상태로 둠, 렌더 사전 검사에 클립 크기 포함 |

### 4.1 적대적 검토(2차)에서 발견해 고친 결함

| 결함 | 수정 |
| --- | --- |
| 스토리보드 저장 후 모델 단가·허용 길이를 바꿔도 저장 당시 값으로 예상·한도 검사·예약을 해 실제 단가로는 한도를 넘는 요청이 나갈 수 있음 | 예상 화면과 유료 생성 확인(쓰기 잠금 안)에서 현재 확인된 단가로 다시 계산해 저장하고, 작업자는 예약 행의 모델·초·비용이 현재 계산과 같을 때만 예약 행 값으로 보냄 |
| 대기 중 장면이 있는 계획을 다시 저장하면 그 장면의 초·비용이 바뀌어 확인보다 긴 클립이 나갈 수 있음 | 생성 중·결과 불명 장면은 다시 저장해도 값을 바꾸지 않고 변경을 거부 |
| 결과 불명 장면을 다른 프롬프트로 바꾸면 이전 Idempotency-Key가 새 내용에 재사용됨 | 결과 불명 장면은 잠그고 먼저 실패로 확정해야 바꿀 수 있음 |
| 월 한도에 정확히 맞춘 확인이 작업자에서 '한도 소진'으로 취소됨 | 보내는 시점 검사는 이미 예약된 금액을 포함해 한도를 **넘을 때만** 멈춤 |
| 한 번의 작업 주기 안에서 승인 해제·공급사 끄기가 뒤쪽 장면에 반영되지 않음 | 장면마다 쓰기 잠금을 잡은 뒤 설정·준비 상태·모델을 다시 읽음 |
| 제한시간 뒤 상태 확인이 한 번 실패하면 완료됐을 수도 있는 유료 결과를 버림 | 제한시간의 2배까지 상태 확인을 계속하고, 제한시간으로 닫힌 장면도 '결과 다시 받기' 가능 |
| 통화를 바꾸면 이전 통화로 확인한 초당 단가가 새 통화로 읽힘 | 통화를 바꾸면 모든 모델의 확인을 해제해 다시 입력·확인하게 함 |
| 제출 직후 기록 쓰기가 실패하면 유일한 요청 번호를 잃음 | 짧게 재시도하고, 그래도 실패하면 메모리에 보관했다가 다음 주기에 기록(다시 보내지 않음) |
| 받은 파일을 검사하는 ffprobe가 concat·재생목록 형식을 자동 감지해 다른 경로를 열 수 있음 | `-format_whitelist`로 mov/mp4·matroska/webm만 허용 |

| AI 장면 포함 합성의 디스크 부족 안내가 실제 필요량과 다름 | 클립 크기를 포함한 필요량(MB)을 안내 |

| 결함 | 수정 |
| --- | --- |

| 0011 이전 행(해상도 빈 값)이 모델 해상도를 바꾼 뒤에도 같은 키를 재사용 | 그 뒤 모델이 다시 저장되지 않았을 때만 같은 해상도로 판정 |

### 4.7 적대적 검토(8차, 수정 확인)에서 발견해 고친 결함

| 결함 | 수정 |
| --- | --- |
| 결과 불명 뒤 다른 요청(길이 변경)을 429로 실제 보냈다가 취소한 뒤 원래 요청을 다시 확인하면, 429로 나간 키가 다른 요청 내용(다른 길이)으로 다시 나감 | 지금 키를 만든 시도와 요청 내용이 같을 때만 키를 이어 씀(한 키는 한 요청 내용에만) |
| 같은 경우 보낸 적 없는 키를 "결과 불명 요청의 키"처럼 다시 씀(문서와 다름) | 위와 같은 규칙으로 새 키를 쓰고, 그 사이 다른 요청을 확인했으면 중복 방지를 키에 기대지 못한다는 점을 설계 §7.1에 명시 |
| 읽을 수 없는 클립의 '결과 다시 받기'가 실패하면(검증 실패·결과 없음) 멀쩡한 원래 클립을 쓸 수 없게 되고 다음 유료 묶음이 다시 구매함 | 새 파일을 받지 못하면 원래 클립을 '준비됨'으로 되돌림(사용량 행 그대로), 결과가 없으면 다시 받기 제공 중단, 누르기 전에 파일을 다시 확인 |
| Windows는 폴더를 열 때 권한 오류를 내므로 클립 자리의 폴더가 '읽을 수 없음'으로 판정됨(7차 테스트가 Windows에서 실패) | 권한 오류여도 폴더면 '없음'으로 판정, Windows 동작을 흉내 낸 테스트 추가 |
| 받지 못한 유료 결과가 있는 장면의 합성 승인 거부가 "기다리거나 카드로 바꾸세요"만 안내 | 장면 상태별로 관계 검토 / 결과 다시 받기·버리기 체크를 안내 |

검토에서 결함이 아니라고 판정한 항목: 공급사가 같은 다시 보내기를 거부(429 4번·401·402)한 뒤의 다음 확인은 새 키를 받는 점(실제로 보낸 마지막 시도가 결과 불명이 아니므로 문서대로이고, 새 요청은 사용자가 비용 화면에서 다시 확인하며 한도 안에서만 나감), 읽을 수 없음 거부 직후 같은 화면에 '결과 다시 받기'가 바로 보이지 않는 점(새로 고치면 보이며 안내서에 명시).

### 4.8 적대적 검토(9차, 수정 확인)에서 발견해 고친 결함

| 결함 | 수정 |
| --- | --- |
| 공급사에 결과가 없거나 다시 받기를 3번 쓴 뒤 되돌린 클립이 여전히 잠겨 있으면, 승인 거부가 화면에 없는 '결과 다시 받기'를 안내하고 버리기 선택을 알려 주지 않음 | 그 장면에 다시 받기가 보일 때만 그 버튼을 안내하고, 아니면 프로그램 닫기·권한 확인 또는 버리기 체크 후 카드를 안내(안내 문장도 같게) |
| 디스크 공간 부족으로 다시 받기가 막혀 되돌린 경우 "다른 프로그램 닫기"만 안내 | 되돌린 이유에 맞춰 디스크 공간 안내를 붙임 |
| 공급사에 결과가 없다는 기록(`result_gone`)을 승인 때 지워, 다시 잠기면 성공할 수 없는 다시 받기를 다시 제공 | 승인 때는 `unreadable`만 지우고 `result_gone`은 유지 |
| `result_gone` 장면의 파일이 나중에 사라지면 다시 받기 가능 장면으로 바뀌어 비용 화면이 "추가 비용 없이 받을 수 있음"이라고 안내하고, 누르면 다시 404 | `result_gone`이면 다시 받기 불가, 새 유료 생성 대상으로 따로 안내, 거부·장면 문장도 그에 맞춤 |

검토에서 결함이 아니라고 판정한 항목: 결과 불명 뒤 장면의 모델·소재를 바꿨다 되돌리면 키를 지우는 점(1단계부터의 동작, 키는 보조 수단이며 다시 보내기는 사용자 확인 필요 — 설계 §7.1 문장을 이에 맞게 고침), 공급사가 거부한 다시 보내기 뒤의 새 키(§4.7과 같음), 결과 불명·미확인 장면의 승인 거부 문구(기존 동작, 다음 할 일을 화면이 따로 안내).

### 4.9 적대적 검토(10차, 수정 확인)에서 발견해 고친 결함

| 결함 | 수정 |
| --- | --- |
| 다시 받기를 3번 모두 써 되돌린 클립의 파일이 사라지면, 장면·거부 문장이 화면에 없는 '결과 다시 받기'와 버리기 체크를 안내 | 다시 받을 수 없는 경우 전용 문장(카드·새 생성 안내)으로 분리 |
| 안내서 '생성 영상 파일을 지금 읽을 수 없음' 행이 다시 받기를 쓸 수 없는 장면에도 그 버튼을 안내 | 버튼이 나타날 때만 쓰고, 아니면 프로그램 닫기·버리기 안내 |

검토에서 결함이 아니라고 판정한 항목: 승인 때 파일이 없으면(나중에 되돌려 놓을 수 있는 경우 포함) 클립 참조를 푸는 점(1단계부터의 문서화된 동작이며 사용 안내가 데이터 폴더 이동 때 `ai-clips` 복사를 요구), 다시 받기 중 공급사 결과가 사라지면 새 유료 묶음에 들어가는 점(비용 화면 확인이 필요하며 한도 안에서만 나감).

## 5. 남은 한계 (구현하지 않음)

- `newsflow.migrate_data`는 DB와 세션 키만 복사합니다. `data\ai-clips` 폴더와 `video-ai-key.dpapi`는 이전 도구가 복사하지 않으므로 데이터 폴더를 옮길 때 사용자가 함께 복사해야 합니다(기존 영상 출력 폴더와 같은 정책).
- 받은 클립은 계획이 참조하는 동안 보관하며, 참조되지 않는 파일만 시작 시 지웁니다. 오래된 계획의 클립을 자동으로 지우는 보관 기간 정책은 없습니다.
- 월 한도는 OpenAI 토큰 한도와 같은 UTC 월 기준(한국 시간 매월 1일 09:00 초기화)이며 화면에 그렇게 안내합니다.
- 실제 Higgsfield 호출, 가격, 생성 품질, 결과 보관 기간은 사용자 승인 전까지 확인하지 않습니다(NOT VERIFIED). 자세한 내용은 [Higgsfield API 검증 결과](phase5d_higgsfield_api_verification.md)를 참고하세요.
